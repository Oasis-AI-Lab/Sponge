## 1. 为什么需要 Move Up

**已有事实（范式层）**：Sponge 的定位是把智能体从「对话式问答机」重构为栖息于信息空间的系统——「agent 不把世界拉进上下文（阅读），而是住在一个外部化、持久化、结构化的世界里（栖息）」（[00 §一·§三](00_总论与野心.md)、[02 §3.9](02_概念与抽象类.md)）。对话式范式被明确列为四大失效范式之一，其失效模式是「无法建构，只能回应；没有目标树、状态、权重」（[01 §二](01_范式论证.md)）。

**已有事实（机制层）**：本仓的不变量是「会话日志是唯一权威」＋「模型可见即已记录」。09 §V.4 由此列出了半解决的第①项：**没有「一个东西拥有一份自己的、可被别的东西读的状态」这种对象**；09 §VI.4 进一步判定「插件拥有自己的世界」在本仓前提下不成立，除非那个世界是「空间里的一份被归属了的状态」。

**本文假设**：如果所有内容都只以对话文本的形式存在，那么「未来仍然需要存在、被引用、被修改、被执行、被验证」的东西就没有独立的生命周期——它只能作为文本被重新阅读、重新解释、重新争论。范式层的野心（栖息而非阅读）与机制层的缺口（没有对象级状态）指向同一件事：**需要一个机制，判定并执行「从对话内容到空间中独立存在」的转移。** 本文把这个转移命名为 Move Up。

**边界**：Move Up 不等于「提取信息」，也不等于「总结对话」。提取问「这段话里有哪些信息」，总结问「这段对话说了什么」，Move Up 只问一件事：**这个东西是否已经值得脱离对话文本，成为空间中的独立存在。** 因此 Move Up 的判断标准不是「重要不重要」，而是「未来是否仍然需要它以独立对象的形态存在」。

## 2. Move Up 是什么

**定义（工作定义，未定案）**

> **Move Up：把对话中的某个语义单元，从「仅存在于 Conversation 中的语言内容」，提升为 Sponge 信息空间中一个可以独立存在的对象。**

**形态（当前理解，未定案）**

```text
Conversation
    ↓
Semantic Chunk
    ↓ Move Up
Space Object
```

### 2.1 例子

| 对话中的表达 | 通常形态 | 是否值得 Move Up | 若 Move Up，可能成为 |
|---|---|---|---|
| 「这个想法挺有意思。」 | 对话内容 | 否——脱离原对话后无法被明确指代，也不会有后续处理 | —— |
| 「NPC 的独立性可能影响玩家对角色真实性的感知。」 | 对话内容 | 可能——可以脱离原对话被独立讨论、验证、修改 | 一个 Hypothesis |
| 「那我们就做一个 A/B 实验验证它。」 | 对话内容 | 可能——它天然有状态、会被执行、会有结果 | 一个 Experiment |
| 「那就测试 NPC independence。」（空间中已存在 Experiment E17） | 对话内容 | 可能是**更新**而不是新建 | `E17.status = planned` |

### 2.2 与相邻概念的区别（本文不做的事）

- **不是信息提取**：提取的产物仍是内容（一张信息表），Move Up 的产物是**获得生命周期的东西**。
- **不是摘要**：摘要压缩的是对话，Move Up 改变的是存在形式。
- **不是分类器**：见 §6——本文明确不把它写成 `Move Up / Don't Move Up` 的二分类。
- **不预设对象类型**：Space Object 落地为切片、元素、还是某种域配置下的切片，本文不给答案（见 §8），也**不**把 [09 §III.1](09_可运行插件原语研究.md) 的五类（Thinking Method / Workflow / Representation / Persistent Process / Interaction Mode）定义为 Move Up 的输出类型——那五类只是「未来可能出现的 Space Object 类型」，且 09 自己标注它们非定论。

## 3. Move Up 的核心思想

### 3.1 从「语言中的存在」到「空间中的存在」

语言中的存在与空间中的存在，差别不在信息量，而在**能被怎么对待**：

| | 语言中的存在（Conversation） | 空间中的存在（Space Object） |
|---|---|---|
| 如何被引用 | 靠再次提及、靠上下文回指 | 有身份，可被其他对象引用 |
| 状态 | 没有自己的状态；状态就是对话内容本身 | 有一份可被归属的状态 |
| 修改 | 只能通过继续说下一句来「修正」 | 可被直接修改，且修改有痕迹 |
| 执行／验证 | 不能 | 可被作为行动依据、实验对象、其他对象的输入 |

**假设**：Move Up 的价值来自右列，而不是「记得更多」。这与 [00 野心三](00_总论与野心.md)（终结上下文：从阅读到栖息）同构——但同构是**论证上的同源**，不是已证明的机制等价。

### 3.2 重点是「生命周期」

Move Up 的产物不是一段更好的文本，而是一个**获得生命周期的东西**。生命周期至少意味着：存在（可被引用）→ 可变（可被修改）→ 可执行或可验证 → 终止或归档。

**已有事实（可作底座，但不等于答案）**：切片契约已给出容器级的生命周期 `[未持久化] → create → [活动 Active] → persist → [持久化 Persisted]`，并给出成员关系唯一、SliceId 持久化后不可变等不变式（[切片契约 §2.1 · §4](契约/切片-Slice-契约.md)）。

**未决**：一个 Space Object 的最小生命周期是什么，本文不给答案（§8 第 4 条）。特别地，切片契约的生命周期描述的是**容器**，而 Move Up 关心的是「一个东西作为对象存在」——两者是否同一件事，未验证。

### 3.3 判别的是「是否值得独立存在」，不是「是否重要」

一次性的解释可能非常重要，但它不需要 Move Up（不会被后续处理）。一个持续研究的问题可能并不紧急，但它需要 Move Up（会被反复引用、修改、验证）。**Move Up 的依据是未来的处理需求，不是当下的语义权重。**

## 4. Move Up Detector

### 4.1 它要解决的问题

> **判定某个 Semantic Chunk 是否已经不应该只作为 Conversation 内容存在，而值得被提升为信息空间中的独立对象。**

Detector 是一个**候选机制**，不是已定案组件。它目前需要研究的不是「算法怎么写」，而是「判定应当依据哪些信号、需要多大的置信度、以及判定结果应当导致什么动作」。

### 4.2 输入与上下文

- **输入**：Semantic Chunk。⚠️ Semantic Chunk 本身如何确定是未解决问题（§8 第 1 条）——边界先于判定，切不出单元就无法判定单元。
- **上下文**：当前信息空间的状态。理由是 §6 的 Resolve：只有知道空间里已有什么，才能区分「创建」与「更新」。

### 4.3 与 09 §IV.3 判据的区别（勿混淆）

两者都是「值不值得变成对象」的判定，但判的不是同一件事：

| | [09 §IV.3](09_可运行插件原语研究.md) 的 C1–C4 | Move Up Detector |
|---|---|---|
| 判什么 | 一个「方法」要不要变成**正在运行的对象**（装上之后的事） | 一段对话内容要不要**离开对话**（装进去之前的事） |
| 时间位置 | 装载时／设计时 | 对话进行时 |
| 失败代价 | 装了一个不需要运行时的东西（包装） | 留下了一堆没人用的对象，或丢掉了该留下的东西 |

两者的关系是**相邻而非同一**：C1–C4 的输入已经是一个「方法」（一个候选装载物），它判的是「要不要给它运行时」；Detector 要回答的是更前面的一步——「它是否值得成为一个候选」。这个区别是本文的推断，不是 09 的结论。

## 5. 当前候选判断信号（candidate signals / research hypotheses）

> 以下五条是**研究假设**，不是最终算法，也不是评分表。列出它们的目的是给出可被证伪的方向。**本文不给权重、不给阈值、不给组合规则**——这是刻意的（§8）。

### 5.1 独立性

这个 Semantic Chunk 脱离原对话后，是否仍然能够被明确理解、指代？

「这个想法不错」通常缺乏独立性——「这个」依赖对话上下文。可检验的问法：它能否被单独拿出来，作为一个可以被署名、被引用、被反驳的单元？

### 5.2 持续性

它是否可能在未来继续被处理、讨论、修改？

一次性的解释通常不需要 Move Up；一个持续研究的问题可能需要。注意：持续性指**未来的处理需求**，不是内容本身的重要性。

### 5.3 状态性

它是否天然存在生命周期或状态变化？

```text
proposed → active → tested → supported / rejected
```

如果一个东西天然会经历状态变化，它更可能值得成为 Space Object——因为状态需要一个可以被归属的载体（对照 09 §V.4 ⚠️① 的缺口）。

### 5.4 后续作用

这个东西未来是否可能成为：行动的依据／实验的对象／另一个对象的输入／表示结构的一部分／后续讨论的引用对象？

如果它未来会持续影响信息空间，Move Up 的价值更高。这一条与 5.2 相邻但不同：5.2 问「会不会再被碰」，5.4 问「再被碰时它会扮演什么角色」。

### 5.5 语义承诺

不同表达的承诺程度不同，它们不能被视为相同强度的语义状态：

```text
「也许可以试试。」
「我认为应该测试这个。」
「好，我们就做这个实验。」
```

**假设**：Detector 应当考虑语义承诺程度。**边界（刻意留白）**：本文**不设计 commitment taxonomy**——不给出档位、不给出判定规则。目前只记录「承诺程度是需要考虑的信号」，以及「三句话不能等价处理」这一条约束。

## 6. Detector 的候选输出

### 6.1 不做二分类

**明确否掉**：

```text
Move Up / Don't Move Up
```

原因：置信度不足时二分类必须二选一，要么漏掉该提升的东西，要么制造大量无价值对象。这两种失败模式代价不同但都很高（§8 第 5 条）。

**当前值得研究的候选输出**：

```text
Stay / Move Up / Ask
```

| 输出 | 含义 |
|---|---|
| **Stay** | 继续留在 Conversation。 |
| **Move Up** | 已经具有足够强的独立存在理由，可以创建或更新 Space Object。 |
| **Ask** | 系统认为它可能值得提升，但置信度不足，应让用户确认。 |

⚠️ 未决：Ask 应当是兜底路径还是主路径？三值是否足够（是否还需要「稍后再说」这类延迟状态）？（§8 第 2 条）

### 6.2 必须考虑 Resolve

Move Up **不一定**意味着「创建一个新对象」。系统还必须考虑：**这个东西是不是已经存在于空间？**

例：用户说「那就测试 NPC independence。」如果空间中已存在 Experiment E17，正确行为可能不是创建 E18，而是 `E17.status = planned`。

因此当前理解的链路是：

```text
Conversation
    ↓
Semantic Chunk
    ↓
Move Up Detector
    ↓
Create / Update / Stay / Ask
```

**已有事实（约束，不可绕过）**：Resolve 命中已有对象后的修改动作，其可改性受**域**约束——待进化域里可自由改，确定域里受限（[02 §3.8](02_概念与抽象类.md)）。本文不假设 Move Up 能绕过这条轴。

**边界**：Resolve 是当前需要研究的概念，本文**不设计具体实现**（不做实体消解的算法）。它与几个已有开放问题相邻但不同：[06 P1-7](06_开放问题与决策.md)「运算域能否固化为切片」问的是**瞬态操作数的持久化**（[03 §五](03_架构与生态位.md)、[07 §五 S2](07_编辑器规划.md) 的「框选→运算→固化」），本文问的是**对话内容的独立存在化**。两者共享一个母问题——「什么条件下一个东西从瞬态变为持久」——但本文不主张它们是同一个机制。

## 7. 一个完整例子

> ⚠️ 这个例子是**为展示链路而构造的**，不是已验证的行为记录；`E17`／`H12` 是虚构 id。

**对话**

1. 用户：「我觉得 NPC 如果只说自己的台词，玩家会感觉他们是道具。」
2. agent：「这个判断可以拆成一个更明确的命题：NPC 的独立性可能影响玩家对角色真实性的感知。」
3. 用户：「对。那就测试它——做一个 A/B 实验，两组 NPC，一组有独立日程。」
4. agent：「空间里已有一个实验 E17『NPC 自主性对沉浸感的影响』，尚未启动。」

**逐步判定**

| # | Semantic Chunk | Detector 判断 | 依据信号 | 空间变化 |
|---|---|---|---|---|
| 1 | 「玩家会感觉他们是道具」 | **Stay** | 独立性弱（依赖对话上下文与用户的个人直觉）；无状态；尚未形成可讨论单元 | 无 |
| 2 | 「NPC 的独立性可能影响玩家对角色真实性的感知」 | **Move Up**（Create） | 独立性强（可脱离对话被单独讨论）；持续性（可研究）；后续作用（会成为实验的输入） | 创建 Hypothesis `H12` |
| 3 | 「做一个 A/B 实验验证它」 | **Move Up**（Update） | 状态性（实验天然有状态机）；语义承诺强（「就做这个」）；后续作用（会被执行） | Resolve 命中已有 `E17` → `E17.status = planned`；`H12` 成为 E17 的输入。**不创建 E18** |
| 4 | 「已有一个实验 E17，尚未启动」 | **Stay** | 是关于已有对象状态的陈述——它的正确归宿是 E17 自己的状态字段，而不是一个新的对象 | 无 |

**后续（展示「被引用 / 被修改」）**

- 三周后，实验被执行，结果写入 E17。`H12` 被引用为 E17 的假设来源；
- 用户说：「H12 是不是太模糊了？」→ Detector 判定 Move Up，Resolve 命中 `H12`，结果是**修改** `H12` 而不是新建一个假设；
- 用户说：「今天先聊到这儿。」→ Stay。

**这个例子想说明的两件事**：① Move Up 的产物不一定是新对象——Resolve 可能把它导向更新；② 判定发生在每一次对话推进中，而不是对话结束后的一次批处理（⚠️ 后者是本文的假设，不是已验证的结论）。

## 8. 当前未知问题

> 本节是本文最重要的部分。以下问题**没有答案**；它们的存在不削弱 Move Up 这个思想，只是在说明它目前还不是设计。

| # | 问题 | 为什么关键 | 当前状态 |
|---|---|---|---|
| 1 | **Semantic Chunk 如何确定？** | 边界先于判定——切不出单元就无法判定单元。切得太细会产生碎片，切得太粗会吞掉本该独立的两个东西 | 无方案。本文整篇建立在这个未定义的单位上 |
| 2 | **何时应该自动 Move Up，何时应该询问用户？** | 决定 Ask 的地位：Ask 是兜底还是主路径。也决定用户的认知负担上限 | 无判据。已知相邻事实：本仓已有人机中断原语（`ctx.userQuestions`、approval） |
| 3 | **什么类型的内容最适合 Move Up？** | 如果所有类型机会相等，Detector 就不需要类型意识；如果不相等，就需要 | 无数据。⚠️ 明确不做的事：不把 [09 §III.1](09_可运行插件原语研究.md) 的五类定义为 Move Up 的输出类型 |
| 4 | **Move Up 后对象的最小生命周期是什么？** | 生命周期是本文的核心主张（§3.2），但没有最小定义；没有它，「Space Object 存在」这句话不可检验 | 候选底座：切片契约的容器生命周期（[契约 §4](契约/切片-Slice-契约.md)）；是否够用未验证 |
| 5 | **如何避免产生大量无价值对象？** | 反向失败模式。对象泛滥会让信息空间变成垃圾场，并让 Resolve 的成本上升 | 无机制。与 [09 §IV.4](09_可运行插件原语研究.md) 的否证线同构（「说不出不装它会更差」→ 就不该装） |
| 6 | **如何识别已有对象并更新，而不是重复创建？** | 这是 Resolve 的实质。做不到，第 5 条的失败模式会指数放大 | 无方案。语义层等价于实体消解问题，本文不假设有解 |
| 7 | **Move Up 是否应完全由 AI 判断，还是允许用户主动触发？** | 决定这是「AI 能力」还是「用户工具」，也决定 Ask 的角色 | 有相邻先例但未定同一：用户主动触发的持久化路径见 [07 §五 S2](07_编辑器规划.md) 的「框选→运算→固化」，其持久化对象是运算域而非对话内容（[06 P1-7](06_开放问题与决策.md)） |
| 8 | **Move Up 是否应作为 Sponge 的原生默认 Plugin？** | 决定它是平台能力还是可选装配物 | ⚠️ **目前只是一个当前方向，不是结论。** 且 Plugin／Element 的边界本身未定（[06 P1-5](06_开放问题与决策.md)） |
| 9 | **被 Move Up 的对象，其状态归属在哪？** | 本仓以会话日志为唯一权威，「插件私有状态」已被判定不成立（[09 §VI.4](09_可运行插件原语研究.md)）；那么 Space Object 的状态必须落在「空间里一份被归属的状态」上 | 与 [09 §IX Q3](09_可运行插件原语研究.md)（域要不要承担状态归属）是同一个未决问题，不是新问题 |
| 10 | **Detector 的判定本身需要被记录吗（可解释性）？** | 若 Detector 会主动创建对象，用户需要知道「为什么刚才那句话变成了一个对象」 | 无方案。相邻约束：[09 §II.7](09_可运行插件原语研究.md) 记录的 Norman 1994「agent 必须可见、可控、能说明意图」与 §V.4 的「主张必须可解释」给出同一方向 |

## 9. 本文不做的事（边界）

这份文档不是：

- API 设计；
- Schema 设计；
- Detector 的最终算法（本文**刻意不给权重、阈值、评分表、分类器结构**）；
- Prompt 设计；
- UI 设计；
- 完整生命周期设计；
- 插件架构设计。

本文特别不做两件事：

1. **不把「Move Up = 某一种具体分类器」写死。** §6 给出 `Stay / Move Up / Ask` 只是当前候选输出集；它可能被证伪、被替换、被扩充。
2. **不把五类对象（Method / Workflow / Representation / Persistent Process / Interaction Mode）定义为 Move Up 的输出类型。** 那五类是 [09 §III.1](09_可运行插件原语研究.md) 的调研对象，且 09 自己标注其非定论；它们只是未来可能出现的 Space Object 类型。

本文只做一件事：**把 Move Up 与 Move Up Detector 作为 Sponge 的一个新研究方向正式记录下来，并准确表达目前已经形成的思想。**
