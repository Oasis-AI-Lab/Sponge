# 07 Sponge Editor 与 Portal 规划（容器的两个窗口）

> 归属：Sponge 论述 ｜ 状态：定位校准 + 规划（2026-08-23）｜ 性质：工程·规划
> 阅读顺序：00（容器/栖息）→ 02 §3.5（原生表征=脚手架）→ 04（调度/固定层）→ 本文。

## 一、定位（校准 2026-08-23：Sponge = 容器）

> **Sponge 是可以容纳无数 agent 与各种抽象类的容器（信息空间）——agent 不是它的使用者，是它的居民；抽象类不是它的分类学，是它的内部构造。**

容器的两个窗口（定案 2026-08-23）：
- **Sponge Editor（创造面）**：脚手架（原生表征）的操作面——结构级 IDE：搭建和修改切片、元素、管线，产出场景（表征应用）；AgentPark 的双面入口（人类 UI + agent 工具面）；
- **Sponge Portal（标准面）**：表征应用的日常入口——用户与 agent 协作、使用 WAM / Lemma 等表征应用的常态界面（Coworker 面）。

两者都搭建在 **DeepSeek Harness** 之上，设计哲学分别对应 Harness 的「创造模式」（cordis preset）与「标准模式」（standard preset）；**借用 Harness 的 UI 壳，但绝对不是一个东西**（D-L）。

## 二、与脚手架的关系（核心）

> 脚手架 = 语言；编辑器 = IDE；表征应用（WAM / Lemma / Glora）= 用这门语言写的程序；中央调度器 = 运行程序的引擎。

- 编辑器的一切操作 = 对原生表征（切片/元素 + 原生元数据）的读写——不发明私有格式，编辑的就是脚手架本身；
- 编辑器产物（场景 / pipeline）天然可被翻译器、信息源、调度器处理——因为产物就是脚手架内容。

## 三、编辑对象、主体与边界

**编辑对象**：切片树（组织）与 kind（子类化）；元素（功能单元）；管线（pipeline DAG——AgentPark/演化层内容，最核心）；场景（面向主体的表征，产物）；域（待进化自由编辑、确定域走审批）。

**主体**：用户（Coworker——人机协同搭建/调整）；agent（FullyAgent——经工具面自我改造结构）；双形态 = 同一编辑器的两种主体配置（"形态是配置"在编辑器上的体现）。

**边界（不是什么）**：
- 不是调度器——护城河在调度器（编排/主动释放/演化）；编辑器改结构，调度器驱动结构，经事件协议对接；
- 不是 Glora 本身——Glora 是应用层语义画板（Sandboxer 组件，可被别的框架承载）；编辑器是范式层画板，Glora 可成为其上的第一个应用；
- 不是内容浏览器——编辑的是结构（拓扑/依赖/管线），不是只读视图；
- 不是 DeepSeek Harness——只是借用其 UI 壳（apps/web + agentPreset 体系），Sponge 核心（切片/域/调度器/信息空间）完全自主。

## 四、与 DeepSeek Harness 的关系（定案 2026-08-23：在 Harness 上搭建，借 UI 壳）

```
DeepSeek Harness（UI 壳 + 前端包：apps/web + ui-sponge-* 客户端插件）
   │  Remote / 服务对接
   ▼
Sponge 核心（★ 独立仓：信息空间 / 切片·域 / 主体 / 中央调度器）
   └── 表征应用（WAM / Lemma / Glora……= 场景）
```

**设计哲学对应（借 UI 壳，绝非同一物）**——Harness agentPreset 体系实据（ui-agent-preset locale 原文）：
- **Editor ↔ 创造模式（cordis preset）**："用于创建自定义 Agent preset：具备标准模式的全部能力，并提供运行时检查、插件实验和 preset 创作指导"——Sponge Editor 把同一种"创造"体验用于搭建 Sponge 表征应用；
- **Portal ↔ 标准模式（standard preset）**："功能完整的编码 Agent：文件编辑、Shell、检索、Skills、计划、目标、子代理、工作流"——Sponge Portal 提供表征应用的日常使用面；
- 借用的壳：apps/web UI + agentPreset（preset = 一个会话的 agent 所运行的插件组装——工具、提示词、能力）；**借壳不借魂**——Sponge 的切片/域/调度器/信息空间完全自主。

- **Harness 契合点**：一切即插件（哲学同构）、self-modification（AgentPark 雏形）、bundle（"插件独立进化"的安装形态）、LSP（编辑器语言服务底座）、session/工具面/subagent/workflow（运行时底座）；
- **Harness 缺的（= Sponge 自主增量）**：信息空间（容器本体）、中央调度器（护城河，自主开发）、切片/域模型、Editor/Portal 的 Sponge 语义；
- **风险**：UI 是重资产（10k 行预算压力主要在编辑器）；UI 层大概率不在 Harness 进程内（消费其 API）；✅ 调度器独立性已定（D-N：核心独立仓）。

## 六、设计公理（2026-08-23 定稿）

> **操作简单是硬指标——不是"东西少"，而是"复杂度被系统吸收"。哲学很深，操作很浅，开发很难——三者缺一不可。**

- 认知可建造（00 野心二）在工具上的兑现："让搭建简单是编辑器系统的功劳，不是用户的负担"；
- 深度住在系统里，用户只做最简单的那层动作。

## 七、为什么"操作简单"反而更难开发（复杂度转移清单）

复杂度没有消失，搬进了系统里：
1. **自由容器 → 具体观感**：通用结构（自由容器）必须被投影成具体形态（WAM 六步循环流程图、Lemma 课程管线）——投影/解释层是最难的工程；
2. **不可见层的信息设计**：Glora 组件带不可见层（类型/来源/置信度/假设/约束，03 五）——该看的看得见、不该看的藏得住；
3. **双面同构**：人类编辑面（UI）与 agent 工具面（工具）共用同一结构，能力必须对称——等于同一套系统做两套接口；
4. **对接层**：编辑一个动作要校验不变式、查域权限、触发翻译、发事件给调度——用户感知是"画了一条线"，系统做一整套；
5. **心流是验收标准**：Sandboxer 笔记原话"用户在使用 Glora 时会轻易地进入心流"——结构编辑做到心流 ≈ 攻克可视化编程的圣杯。

## 八、路径推论

1. **简单是验收标准，不是起点**——S1 文件级是骨架/内部形态；画布才是"操作简单"的兑现——**画布是目的地，文件级只是它的脚手架**；
2. **10k 行预算的压力主要在编辑器**——投影层、校验层、双面接口、事件对接都是真活，不是 UI 装饰；
3. **"简单"的终极候选（未定论）**：意图式编辑——用户描述需求，agent 用工具面搭出来（编辑器简单到"对话即可搭建"）；方向与权力转移（00 野心一）自洽。
