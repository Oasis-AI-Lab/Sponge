## 三、关键概念的精确边界

### 3.1 切片 vs 运算域
- **切片**：持久、可命名、可子类化的容器；可被 agent 调用。
- **运算域**：用户框选组件形成的瞬态操作数（框选→运算→结束）。
- 开放问题：运算域能否「固化」为切片？

### 3.2 信息源 vs Statuz
- 信息源是 Sponge 的抽象板块**角色**（接口）；Statuz 是**独立实现**——它同时是独立全局状态层，可服务任何 agent 系统。
- 之所以叫「子类」：说明除了 s（Statuz 的运算），还可以有别的运算 → 可替换性（约束 3）。
- **关键独立性承诺**：接口定义不依赖 Statuz；Statuz 只是实现之一。

### 3.3 切片的职责边界
- **负责**：组织单元、承载元素、可子类化、持久化、命名。
- **不负责**：不解释语义（表征层/调度的职责）；不决定何时释放（调度系统的职责）；不存储「当下状态」（信息源/Statuz 的职责）。

### 3.4 场景（Scene）
- 最容易理解的抽象类：面向用户的表征。
- 例：Lemma Engine 为用户提供的多种学习方式；WAM 为用户提供近乎无限种类的思考 Pipeline——**都是场景的实例**。
- **推论**：场景的存在证明地基不感知上层是谁——WAM 和 Lemma 只是场景抽象类下的两个实例。

### 3.5 原生表征 = 脚手架（2026-08-23 定案）

- Sponge 的原生表征是一个**脚手架**：切片/元素构成的通用结构框架 + 原生元数据（可全部操作的保证）。
- 脚手架刻意轻、通用、不预设内容类型（对齐切片「自由容器」）；「脚手架可以被复制，调度系统是护城河」（00 野心二）。
- **边界**：翻译器做**内容物化**（外部→脚手架），信息源做**状态供给**（结构→当下状态）——方向与层次不同；翻译器**不改结构**，改造是通道的职责（04 六）——**转换 ≠ 改造**。
- 层级分工：翻译器（Sponge 层）做**通用脚手架化**；应用层（表征应用，如 Sandboxer 的 Glora Native）在脚手架之上做**领域深加工**。
- 翻译器的输出 = 脚手架构件。

### 3.6 接收器 vs 翻译器 vs 信息源（2026-08-23 修正）

- **接收器**：接受外部**不可控**信息的接收入口（如 BBC 新闻专栏）——系统管不了外部发什么；只**引入**，不改变信息性质。
- **翻译器**：把信息**物化**为原生表征（脚手架）——完成「不可控 → 可控」的跃迁。接收器回答「信息怎么进来」，翻译器回答「进来的信息怎么变成我们能操控的形态」。
- **信息源**：**内部可操控**的信息——Statuz 是实例；系统可 traverse/impact/path。**接收器与信息源关系不大**：一个是外部入口（不可控流入），一个是内部状态层（可控资产），中间隔着翻译器完成的控制性跃迁。
- 管道：外部世界 → 接收器（引入）→ 翻译器（物化）→ 原生表征 → 信息源/Statuz（当下状态）→ 调度 → agent。

### 3.7 主体与域（2026-08-23 提案，待团队定稿）

**主体（Subject）**：用户与 agent 的共同抽象类。
- 源头：Sandboxer 8/17「身份组」构想——"把用户和 Agent 放进同一个'观察'组里"；
- 共同本质（候选）：都是**行动者**（能主动发起动作）、都有**身份**（可识别、可授权）、都有**视角**（鸿沟「场域叠加」：每个人都有视角）；
- 与双形态（03 四）：**形态 = 主体组合的配置**——FullyAgent = 仅 agent 主体；Coworker = 用户主体 + agent 主体共享世界；
- 与权限（04 三）：主体是权限的载体——用户主体可改固定层，agent 主体默认只能改演化层，越界走审批（主体间交互）；
- 与场景（§3.4）候选：场景泛化为「面向主体的表征」（agent 的工具面也是主体的场景）；
- 与「调用主体中立」（06 D-I）：翻译器/接收器的"调用主体"字面化 = 主体抽象类；
- ⚠️ 张力：02 称「切片是所有抽象类的基类」——主体从切片派生则用户是切片；或主体在切片之外（行动者拥有切片，非容器）。待定（06 P1-9）。

**必要性评估（2026-08-23 审视记录）**：**必要但可后置**。
- 范式核心主张（C1-C5）没有一个严格需要主体抽象；正当理由是**多主体场景**——研究底座（Statuz 笔记：John/Mike/Jack/Zames 多 agent 团队）与 Coworker（03 四）无法在没有"行动者可区分性"时表达；
- 单 agent 长周期任务（MVP 证伪实验，01 六）不需要主体抽象；
- ⚠️ 变量：若 MVP 最小表征应用（apps/）选人机协作场景，主体就进入 MVP。

**形式评估（2026-08-23 审视记录）**——存在形式谱系：`字段 → 域 → kind → 抽象类`（右移概念加重）：
- **抽象类形式：不推荐**——宪法张力（「切片是所有抽象类的基类」）+ 抽象动物园增员 + god-class 风险（身份/权限/视角都想往里塞）；
- **域形式（候选推荐）**：不增类、宪法不动；双形态=域配置（FullyAgent=仅 agent 切片处于主体域；Coworker=用户+agent 切片同处主体域）；权力转移=域迁移（切片主体化=结构层面的权力转移，与「自我演化不需要改权重，改结构就够了」同构）；元进化引擎=外部系统切片化后再主体化；权限不对称进 authority 字段（human=最终权威，agent=被委托）；
- **字段形式（MVP 落点）**：`owner` + `role`，几十行，先跑起来；
- 路径建议：MVP 先字段；第一个多主体场景（研究底座/Coworker demo）要求"主体性是可迁移状态"时，域形式转正。
- **定案（2026-08-23）**：主体性=能动性=模式 → 按 §3.8 判别式取**域形式（主体域）**；MVP 仍先字段实现。

**域（Domain）**：非抽象类，是**另一个层级**——内容成熟度/可改性的横切属性。
- 例：**确定域**（已定，改动受限——走契约修订流程）、**待进化域**（可自由演化）；
- 与固定层/演化层（04 三）的机制化对应：确定域 ≈ 固定层语义，待进化域 ≈ 演化层语义；域迁移 = 演化的「封版」动作；
- 与通道（04 六）：待进化域里通道自由，确定域里通道受限——域给改造语法加上权限维度；
- **轴读法（2026-08-23 定案）**：域 = **能动/权限模式轴**——待进化=被自由操作、确定=被限制操作、**主体=主动操作**（主体域为第三值），一根轴（已随 §3.8 正式定义采用）；
- ⚠️ **「主体化」迁移是投机**：内容→主体的迁移规则（谁批准获得能动性）目前只有元进化引擎需要，MVP 用不上，不作承重墙；
- ✅ 命名冲突已化解：运算域按 §3.8 判别式重分类为域（瞬态模式，非抽象类）——不存在两个"域"同名（06 P1-11 已结）；
- ⚠️ 与「场域叠加」（鸿沟：游戏视角）无关，仅字面相近。

### 3.8 抽象类 vs 域：正式区别（2026-08-23 定稿）

**抽象类（Abstract Class）**：实体**类型**的分类——回答「这个实体**是什么**」。定义接口、职责边界、不变式与生命周期；同类实例共享结构与操作契约。切片是所有抽象类的基类。抽象类之间是**分类关系**：派生（subclass）产生新类型的实体。

**域（Domain）**：非类型概念，作用于实体之上的**存在模式**——回答「这个实体**处于什么状态、可被怎么对待**」。不定义结构，定义**可改性/能动性**：一条能动/权限模式轴——**待进化**=被自由操作、**确定**=被限制操作、**主体**=主动操作。同一实体可在域之间**迁移**（待进化→确定=封版；内容→主体=主体化）。域**横切**于抽象类之上：任何抽象类的实例都有域（粒度待定，06 P1-10）。

**判别式**（一个概念是抽象类还是域）：
1. 回答「是什么」还是「处于什么状态」？——类型 vs 模式；
2. 定义接口/契约吗？——抽象类定义接口；域定义状态与迁移规则；
3. 实体能在其中移动吗？——域可迁移；抽象类不可（派生产生新实体，不是移动）；
4. 横切所有实体吗？——域横切万物；抽象类分门别类。

**判别式应用（2026-08-23 定案）**：
- 抽象类：切片、元素、信息源、场景、翻译器、接收器、通道、AgentPark（类型）；
- 域：确定域、待进化域（状态）；
- **主体 → 域形式（已定案）**：主体性=能动性=模式 → 取**主体域**（能动/权限轴第三值）；MVP 先字段实现（owner+role），主体域随第一个多主体场景转正；
- **运算域 → 重分类为域（已定案）**：框选→运算→结束是**瞬态模式**而非类型 → 移出抽象类清单，归入域（瞬态域）；命名冲突就此化解。

**与实现的关系**：抽象类 = 接口/契约层（类型签名、方法、不变式）；域 = 状态层（字段 + 迁移规则，如 `domain` 字段 + 迁移动作）。

### 3.9 信息空间 = 容器本体（2026-08-23 定案）

> **Sponge 是可以容纳无数 agent 与各种抽象类的容器（信息空间）——agent 不是它的使用者，是它的居民；抽象类不是它的分类学，是它的内部构造。**

- **容器本体**：信息空间 = Sponge 的存在形态；「栖息」（00 一 / 01 四）是 agent 与容器的关系——居住其中，而非把世界拉进上下文（阅读）；
- **居民**：主体（域形式，§3.7）——无数 agent + 用户，多主体共存是容器天然的多租户属性；
- **内部构造**：抽象类（切片/元素/信息源/场景/翻译器/接收器/通道/AgentPark）——容器里可以长出来的物种；无限子类 = 无限的家具种类；
- **容器壁（对外边界）**：信息源接口——「结构在界内、状态在界外、接口即边界」；
- **壁上的门**：接收器（外部不可控信息入）→ 翻译器（物化为原生表征）、接收器/信息源（出）；
- **嵌套（分形）**：切片本身是自由容器（容器内嵌容器）——「下一个系统是 Sponge 的一个切片」（00 野心四）是字面嵌套；
- **状态轴**：域（§3.7/§3.8）——构造物的待进化/确定/主体；
- **子系统（非本体）**：中央调度器（驱动系统）、Sponge Editor（创造面窗口）、Sponge Portal（标准面窗口）、表征应用（城区，WAM/Lemma/Glora）。

**与抽象类/域的区别**（套用 §3.8 判别式）：信息空间既不是类型也不是状态——它是**容器本身**；抽象类是容器内的类型（是什么），域是容器内的状态（处于什么状态）。
