# 09 可运行插件原语研究

> 性质：**研究**（不是设计、不是计划、不产出 API／目录结构／schema）
> 日期：2026-09-22 ｜ 依据：本仓代码核实（`file:line` 见附录 A）+ 跨领域调研（PL/Runtime、KR/认知架构、AI Agent 系统、HCI/认知科学）
> 与 [02](02_概念与抽象类.md) 的关系：本文**不修改** 02。若结论要求改概念，走 02 的修订流程。
> 目标问题不是「Plugin 应该怎么实现」，而是：**当用户能往一个空间里装"一种思考方式／工作方式／表示方式／持续过程／交互方式"时，出现了什么新的计算原语？**

---

## 0. 结论先行

**一句话**：五类东西里，真正新颖的部分**不是"可运行"**——DSH 已经让任何东西可运行、可挂 UI、可持久化（附录 A）。真正没有现成答案的，是**「多个东西同时在主张下一步该做什么，谁说了算」**。所以候选原语是**「主张者」（claimant）**：一个可挂载、可撤销、引用一份状态、并在每一步主张"下一步／下一屏"的东西；而空间必须新造的不是执行引擎，是**主张的调解**与**状态的归属**。

**三条判据（用来挡住"为统一而统一"）**

| 判据 | 含义 | 反面（做了就是装饰） |
|---|---|---|
| **J1 内核不动** | 新增一种至今没想到的东西，**不改内核**即可装上 | 每加一类要改地基 → 说明地基选错了，不是缺 primitive |
| **J2 判据可测** | 一个方法是否值得做成运行对象，能用四条条件（§IV.3）判别，且有反例 | 说不出"不装它会更差"→ 它就是一个 prompt |
| **J3 差异不可消除** | 能指出至少一个**只在某个模型下说得通**的实例 | 所有实例所有模型都能解释 → 模型之间没被区分开，等于没结论 |

**最小共同结构（候选，非定论）**：五类都满足的只有三条——① **双形**（有声明形态与运行形态，声明即运行时规格）；② **可撤销**（装上再卸下要回到装之前）；③ **会主张**（在某个粒度上主张"下一步／下一屏是什么"）。除此之外的每一条（有没有状态、要不要时钟、要不要视图、要不要权限）都在五类之间**分裂**——见 §III.2 矩阵。

## Part I 问题重新定义

### I.1 问题被问错的两处

**错处一：把"能不能统一"当成主要问题。** 真正决定答案的不是"有没有共同点"（一定有，任何五个东西都能找到抽象），而是**"统一发生在哪一层"**：接口层（怎么装、怎么撤、怎么主张）与机制层（怎么跑、状态存哪、谁触发）是两个不同的统一。§III.2 的证据表明机制层统一不了，而且**不该**统一——因为五类需要的是**三种不同的运行时**（§III.3）。

**错处二：假设"D5 类是一组平级的东西"。** 它们不是平级的。它们沿着**三条互不重合的轴**分布：

| 轴 | 五类的取值为 |
|---|---|
| **轴 A｜主张什么** | Method：主张**问法** ｜ Workflow：主张**过程** ｜ Representation：主张**看见什么** ｜ Process：主张**时序** ｜ Mode：主张**说法（人格）** |
| **轴 B｜状态存哪** | Method：无 ｜ Workflow：过程内 ｜ Representation：**对象即状态** ｜ Process：**它是状态的权威** ｜ Mode：一个 bit |
| **轴 C｜需要什么运行时** | Method／Mode：**不需要**（纯策略／纯过滤） ｜ Workflow：执行器 ｜ Representation：视图 + 校验器 ｜ Process：时钟 + 状态机 |

三条轴上的分布**不重合**，所以能得到的最强结论只能是："它们同处一层（都是被装进空间的东西），但不是同一个东西。"

### I.2 真正决定答案的两个问题

| # | 问题 | 为什么它才是关键 |
|---|---|---|
| **Q1** | 你要统一的是**"装的接口"**还是**"跑起来的东西"**？ | 若是前者：五类可统一，且 DSH 已提供大半机制（§V.2）。若是后者：五个器官必须分开，强行合并会造出一个什么都做不好的东西。**必须先选这个，再谈 primitive。** |
| **Q2** | 空间里同时有 5 个东西都想要下一步时，**谁说了算**？ | 这是唯一**没有现成答案**的问题。业界所有系统对它的回答都很弱（§VI.3），而 Sponge 的调度器（02 §四 / 04 §四）如果要有护城河，它的实质就是这个。 |

### I.3 Sponge 已有的词——别重造

研究前必须先用本仓自己的词对齐，否则会造出与 02 冲突的第三套分类学。**本仓已经写下的答案**：

| 你问的东西 | 本仓已有的位置 | 出处 |
|---|---|---|
| "可运行插件"的物质载体 | `content/` 目录注释：**element（callable units inside slices）** | `研发/impl/PLAN.md:118` |
| 谁决定何时跑 | `mechanism/` = scheduler · channel · agentpark | `研发/impl/PLAN.md:117` |
| 对外部信息 / 表征的角色 | `role/` = infosource · translator · receiver · scene | `研发/impl/PLAN.md:117` |
| "声明"与"实例"的关系 | `runtime/` 注释：**assembly + config（dual form = config）** | `研发/impl/PLAN.md:119` |

### I.4 本文的验收标准

1. 不把五类强行统一（允许结论是"它们不需要统一"）；
2. 每个论断可回溯到 `file:line` 或具名一手材料；
3. 给出 **3～5 个互相竞争的**抽象模型，并给**判别实例**（哪个实例杀掉哪个模型）；

5. 明确标注**未验证**的部分。

## Part II 现有领域研究地图

> 方法：每域只问一件事——**"它把「能力／方法／状态／行为／环境」变成了什么可运行的东西"**。
> 证据等级：**【一】**=一手规格/源码级已核；**【二】**=权威二手（论文/官方文档，已核）；**【待核】**=通识记忆，尚未逐条核对（见 §II.9 待办）。

### II.1 插件与运行时（PL / OS）

| 系统 | 可运行单元 = | 关键机制（对我们的用途） | 等级 |
|---|---|---|---|
| **OSGi R8** | bundle（JAR + MANIFEST） | 显式生命周期 `INSTALLED→RESOLVED→STARTING→ACTIVE→STOPPING→UNINSTALLED`；**一个单元同时声明"我要什么"（`Import-Package`）和"我给什么"（`Export-Package`）**；激活钩子 `BundleActivator.start/stop` | 【二】 |
| **Erlang/OTP** | application（`.app` + 回调模块） | **behaviour = 契约 + 回调**（`init/handle_call/handle_cast/terminate/code_change`）＝"通用部分框架管、具体部分你写"；**supervision tree** 只负责恢复，不负责业务 | 【二】 |
| **Wasm Component Model** | component + **`world`** | WIT 的 `world` **就是能力声明本身**；`resource` 类型有 `own`/`borrow` 句柄语义 | 【二】 |
| **Java SPI / Node ESM hooks** | 发现式加载 | `META-INF/services`（JDK 6）；Node 22.15+ `module.registerHooks`（同步链式 `resolve`/`load`） | 【二】 |
| **Actor（Hewitt 1973 / Agha 1986）** | actor | actor 只拥有三样：**mailbox + 私有状态 + 行为**；合法动作只有四件：收一条消息、发消息、**创建新 actor**、**替换自身行为（become）** | 【二】 |
| **Orleans 虚拟 actor** | grain | **永不显式创建/销毁**，按 id 寻址、运行时按需激活；`OnActivateAsync` 在状态装载**之后**、任何消息派发**之前**；`RegisterOrUpdateReminder` = 跨去激活的持久唤醒 | 【二】 |
| **seL4 / object-capability** | CSpace + capabilities | 权限 = **引用本身**（不是声明）；铁律："**only connectivity begets connectivity**"、"禁止 ambient authority"；已形式化证明 **authority confinement** | 【二】 |
| **Kubernetes / Operator** | CRD + controller | **声明期望态（spec）**，**水平触发调和循环**（level-triggered ⟹ 必须幂等，需要 **finalizer** 做删除前钩子、需要 leader election 唯一活跃） | 【二】 |
| **systemd / Nix** | unit / derivation | 声明式依赖顺序（`After`/`Wants`/`WantedBy`）；Nix：一切输入皆 derivation，产物按内容寻址、可原子切换 | 【二】 |

**可迁移结论**：**"装进去"从来不是一个布尔量，而是一次状态机转移**（OSGi 六个态、Orleans 激活/去激活）；而**"声明要什么" ≠ "被授予什么"**——声明在 manifest 里，授权在基底里（CSpace 槽位 / WASI preopen / OCap 引用）。

### II.2 认知架构与黑板（把"表示"当运行时）

| 系统 | 结构 = | 对我们的用途 | 等级 |
|---|---|---|---|
| **Hearsay-II**（CMU，1971–76；Erman/Hayes-Roth/Lesser/Reddy 1980） | **黑板**（分层假设数据库，每个假设带时间坐标 + 可信度）+ **知识源（KS）**（独立、异步、条件触发的**条件→动作**模块，彼此不直接通信）+ **调度壳**（决定哪个已启用的 KS 先跑） | **表示就是基底**：KS 不是"读黑板"，KS 是被黑板上的模式**触发**的。这是"表征即运行时"最强的一手先例 | 【二】 |
| **BB1**（Hayes-Roth 1985） | 加一块**控制黑板**（把"调度"本身当推理对象） | "谁决定下一步"本身可以被显式建模成对象 | 【二】 |
| **GWT / LIDA**（Baars 1988；Franklin 2007） | 若干 codelet 组成联盟，**竞争容量有限的全局工作区**，胜者被**广播** | 比消息总线多出四样：**稀缺、竞争、胜者、广播** | 【二】 |
| **Soar**（Laird/Newell/Rosenbloom 1987） | **问题空间 + 算子 + 偏好**；决策无法收敛时产生**类型化 impasse** → 开**子状态** → 解决后 **chunking** 把依赖条件编译成新产生式 | 没有"调度器"，用**规则 + 决策周期**替代；子状态天然递归 | 【二】 |
| **ACT-R**（Anderson） | 类型化 **buffer**（goal/retrieval/visual/manual）+ 产生式匹配 buffer 内容 + 亚符号激活值 | 表示 = 基底，同样是"表示驱动运行" | 【二】 |
| **Subsumption**（Brooks 1991） | 分层反应式行为，**明确否认中央表示** | 反例：证明"容器本体"不是唯一解 | 【二】 |

**可迁移结论**：黑板三件套 = **共享结构化状态 + 条件→动作的知识源 + 调度壳**。这是"插件自带世界"的**唯一有长期证据的形态**；而且它明确告诉我们：**一旦有共享状态，就必须有调度壳。** 反过来说，**只有当插件之间需要共享状态时，才需要调度器**。

### II.3 KR：表示能不能"跑"

| 表示 | 惰性 / 可执行 | 证据 |
|---|---|---|
| **RDF + OWL 2** | OWL 是**单调推理过程**：`owl:maxCardinality 1` 遇到两个父亲不是报错，而是**把两个人合并**（开放世界） | 【二】 |
| **SHACL**（W3C Rec，2017-07-20） | **闭合世界校验** + **规则引擎**（`sh:rule`/`sh:order`，可做非单调与有序执行）；输出校验报告 | 【二】 |
| **IBIS**（Kunz & Rittel 1970）/ gIBIS / Compendium；**Toulmin 1958** | **纯记录与导航，从不执行**——论证图没有解释器 | 【二】 |
| **超图 / RDF-star** | 超边 ⇄ 属性图同构（用中间节点实现，即 reification）；RDF 1.2 直接给三元组挂元数据 | 【二】 |
| **语义网络**（Quillian 1968）/ **概念图**（Sowa 1980s）/ **概念图（Novak 1970s）** | 前两者有一阶逻辑语义（可推理），Novak 的概念图是**教学用的层次 + 交叉连接**，不可执行 | 【二】 |

**可迁移结论**：**"能运行的图"与"画出来的图"是两种东西**。判据是：**是否有解释器被绑定到它**（statechart 有 SCXML/XState 引擎；SHACL shape 有校验器；IBIS **什么都没有**）。同一条判据的另一面：**"查询"不是"效果"**——`Dataview` 读图，黑板的 KS 与 Tana 的 supertag 自动化**写回图并改变接下来会发生什么**。

### II.4 状态机与进程代数

**Harel 状态图**（*Sci. Comput. Program.* 8(3), 1987）在 FSM 上加四样：**层次**（复合/超状态，解决状态爆炸）、**并发**（正交区域同时活跃）、**通信**、**历史**（浅 `H`/深 `H*`）。**run-to-completion** 语义（UML 2.5.1）与 **SCXML**（W3C Rec 2015）让它**可序列化、可执行**。**XState v5** 把机器与 actor 合并：`invoke` 可以派生一个子机器/子 actor——**这是"方法有了正式表示 + 绑定解释器"的标准答案**。Petri 网 / CSP / π-calculus / TLA+ 提供**语义与验证**，但标准工具是分析，不是持续运行。

### II.5 活编程与自改（热更的安全边界）

Smalltalk image 里"**开发期与运行期没有区别**"；Racket "Languages as Libraries"（PLDI 2011）证明 `#lang` 只是库。**自改真正会坏的地方**：类重定义后活实例必须**迁移**；Erlang **只能同时存在两个模块版本**（加载第三个会杀掉还跑在旧码上的进程），所以长循环必须 `?MODULE:loop(...)`；image 系统没有多用户事务性。**安全边界**：OTP 的 **`.appup` + `code_change/3`**（升级规程 + 状态迁移）、**监督 = 重启回已知良好态**（而不是原地修复）、Pluto.jl 的"**no hidden state**"（删除定义 = 删除变量）。

### II.6 AI Agent 系统（业界现状）

> **本节待跨领域调研回补细化**（正在跑：MCP / Agent Skills / LangGraph / AutoGen / CrewAI / OpenHands / computer use / 记忆系统 / durable execution / agent harness 谱系）。先给已核的框架级结论：

**(a) 工具面与协议面**：**MCP**（2024-11 起）把服务器能力拆成 tools / resources / prompts 等声明式对象，**由服务器声明、由宿主调用**——即"**能力是数据，不是代码**"。**Agent Skills**（SKILL.md）把方法做成**渐进披露的指令包**（metadata → body → 附件），本质上仍是**知识**，不是运行对象。两者的共同点：**它们是"说明书 + 调用契约"，没有生命周期、没有状态、没有调度**。

**(b) 编排面**：LangGraph、AutoGen、CrewAI 等都把"过程"变成**图或以图等价物表达的显式状态机**，并各自附一个 **checkpointer / store** 承载跨步状态。方向很一致：**过程从"模型的即兴"变成"外部的图"**。（具体一手材料待回补。）

**(c) 托管运行时面**：**durable execution**（Temporal 谱系）是对的解法——workflow-as-code、确定性重放、activity、signal/query、timer、重试；**重放要求确定性**是它的核心约束，也是任何"过程要能恢复"的代价。（待回补。）

**(d) 安全与权限**：目前业界主流是**过程级**授权（一次会话/一次运行给一个权限档），不是**对象级**能力。DSH 的 `agentTeams` 是个反例，它用"**the exact live Agent**"当授权凭证（`docs/subsystems/agent-team.zh.md:98`）——这是**能力式**授权，值得抄。

### II.7 HCI：方法什么时候变成环境

> **本节待跨领域调研回补细化**（正在跑：直接操作、最终用户编程、混合主动、认知工具、分布式认知、信息环境）。先给已核的骨架：

- **直接操作**（Shneiderman 1983；Hutchins/Hollan/Norman 1985）：直接性不是技术属性，而是**距离**（gulf of execution/evaluation）与**参与感**两个变量。→ 对我们：**"用户能直接改这个对象"是表征类插件的必要条件**，只读视图不构成工具。
- **最终用户编程**：**电子表格（VisiCalc 1979）是有史以来最成功的最终用户编程系统**——因为它让"公式"既是**可读的声明**又是**可运行的实例**。这与 Sponge 的"**dual form = config**"（`PLAN.md:119`）是同一条律。
- **混合主动与智能体代人的代价**（Horvitz 1999；Maes 1994；**Norman 1994《How Might People Interact with Agents?》**）：agent 必须**可见、可控、谦逊、能说明意图**。→ 对我们：**任何"主动主张下一步"的东西都必须能解释自己为什么这么主张**——这是硬约束，不是体验优化。
- **认知工具 / 分布式认知 / 延展心智**（Norman 1991；**Hutchins 1995**；Clark & Chalmers 1998）：认知是**系统**的属性，不是人的属性。→ 对我们：**评估单位只能是"人 + 空间"，不是"模型输出质量"**。

### II.8 认知与学习科学：方法自带前提条件

> **本节待跨领域调研回补细化**（正在跑：scaffolding 与 fading、元认知/ICAP/desirable difficulties、论证与思考工具、AutoTutor/Cognitive Tutor、科学方法论）。先给已核的三个结论：

- **脚手架的本质是"撤除"（fading）**：Wood/Bruner/Ross 1976 起，**撤除与偶联是定义的一部分**；进而 **expertise reversal effect**（Kalyuga）——同一个帮助，对新手有效、对熟练者**有害**。
  → **这是本文最有用的一条外部证据**：任何"方法型插件"必须**自带退出条件**，否则它装载越久越有害。它把 J2 变成了一个可测的实验（§X E2）。
- **Salomon/Perkins/Globerson 1991 "Partners in Cognition"** 的区分：**effects WITH technology**（人在用工具时更强）≠ **effects OF technology**（卸载后人也更强）。→ 对我们：**这正是"装/卸"必须成为一等操作的学术理由**——如果不测"卸下来之后呢"，就无法区分工具是帮你还是替了你。
- **"最小指导/探究式学习失效"**（Kirschner/Sweller/Clark 2006）：纯发现式方法在**新手**上反复失败。→ 对我们："苏格拉底法"作为可装载对象，**必须带前置条件（学习者已有足够先备知识）**，否则它是负资产。

### III.1 先收集实例，不下定义

| 类 | 真实实例（跨领域，不只 AI） | 一句话它们共同长什么样 |

### III.2 比较矩阵（A–M）

图例：**有** = 该类自身具备；**无** = 自身不具备；**寄生** = 必须依附他者的状态/触发才能成立；**弱** = 存在但非本质。

| # | 问题 | Method | Workflow | Representation | Persistent Process | Interaction Mode |
|---|---|---|---|---|---|---|
| **A** | 它是什么（见 §III.1） | 策略 | 过程 | 结构 | 权威状态 | 过滤层 |
| **B** | 拥有自己的 State？ | **寄生**（依赖"当前理解"） | **有**（过程进度/中间产物） | **有，且对象即状态** | **有，且它是权威** | **一个 bit**（是否激活） |
| **C** | 拥有自己的行为？ | 有（提问策略，纯函数式） | 有（有向过程） | **无**（惰性，除非绑校验器/规则） | **有，且自发触发** | 有（每轮必执行的改写） |
| **D** | 能改空间里其他对象？ | 不直接（改的是人的理解） | **能**（产物落盘） | **能**（它本身是被改对象，也可作索引改写他者） | **能，且持续** | **不能**（只改"怎么说"） |
| **E** | 能创建新对象？ | 弱（产出新问题） | **能** | **能**（节点/边） | **能**（证据/假设/子目标） | 不能 |

| **G** | 能持续运行？ | 不能 | 不能（一次性 run） | 不能 | **能（唯一）** | **"半能"**：长期激活但被动 |
| **H** | 能暂停/恢复？ | 无需（无状态）；会话层需可恢复 | **需要**（长过程必需） | 天然（存下就是停着） | **必须（这就是它的定义）** | 只是开关 |

| **L** | AI 可主动调用？ | 可（是"说法"） | 可，但**消耗资源且会跑偏 → 需授权** | 可，但**会改变用户看到的世界 → 需授权且可逆** | 可，但**它是权威状态 → 需最高授权** | 可（属于 AI 的说话方式） |
| **M** | 需要自己的 Runtime？ | **不需要** | **需要：执行器** | **需要：视图 + 校验器** | **需要：时钟 + 状态机** | **不需要** |

### III.3 共同部分与不可消除的差异

**共同部分（只有三条）**

1. **双形**：都有"声明形态"与"运行形态"。Semantic 依据：Sponge `runtime/` 的 "dual form = config"（`研发/impl/PLAN.md:119`）；DSH 的 `ui-slots` 原则"**declaring is claiming**"（`packages/client/ui-slots/src/index.ts:141-143`）；外部先例：电子表格的公式（可读声明 = 可运行实例）。
2. **可撤销**：装上再卸下必须回到装之前。DSH 已有：一切注册都是 `ctx.effect()`（`docs/cordis-primer.zh.md:13`）。
3. **会主张**：在某个粒度上主张"下一步／下一屏"。**注意这一条是本文的候选新增**，02 目前没有对应的词。

**不可消除的差异（硬证据）**

| 差异 | 证据 |
|---|---|
| **需要三种不同的运行时** | 矩阵 M 列：只有 Workflow／Representation／Process 需要运行时，且分别是**执行器／视图+校验器／时钟+状态机**——三种不同机制，不是一种机制的三档配置 |
| **触发源不可统一** | 只有 Process 有**自己的时钟**；Mode 是"长期生效但被动"；Method 根本不持续。硬把三者塞进一个"持续运行"模型，会给 Method 强加一个它不需要的生命周期 |
| **状态归属不可统一** | Representation 的状态**就是用户直接操作的对象**（对象即状态）；Process 的状态是**权威真相**（可以被别的插件读）；Workflow 的状态是**过程私有**（跑完就该扔）。三者混在一个 store 里，会立刻产生"谁是权威"的问题 |
| **冲突轴不可统一** | 矩阵 I 列：五类与别人冲突的**轴各不相同**（策略/顺序/投影/归属/人格）。一个统一的 priority 数字解决不了"两个人格冲突" |

### III.4 三个最容易混淆的东西

来自跨领域证据（`general-purpose-3` 简报，三项均为【二】级）：

| 常被混为一谈 | 差别 | 对我们的后果 |
|---|---|---|
| **生命周期钩子 ≠ 持续过程** | `BundleActivator.start()`、`OnActivateAsync()`、构造函数都是**激活时跑一次然后返回**；Elm 的 `Sub`、调和循环、监督者、黑板的 KS 是**持续跑** | 说"加载时运行的东西"时，要问清是**一次转移**还是**一个循环**——这是"Method → Runtime"阶梯上不同的两级（§IV） |
| **声明要能力 ≠ 被授予权限** | OSGi `Import-Package`／WIT `world`／SHACL shape／K8s RBAC role 都只是**描述**；授权在基底（CSpace 槽位、WASI preopen、OCap 引用、校验器） | 插件声明"我要 fs 权限"**不等于**它有；Sponge 的域/权限轴必须落在**谁能持有哪个引用**，不能落在声明里 |
| **可执行表征 ≠ 被表征的行为（查询 ≠ 效果）** | statechart／SHACL shape／论证图在被**绑定特定解释器之前是惰性数据**（IBIS 至今没有解释器）；`Dataview` **读**图，而黑板 KS 与 Tana supertag **写**图 | "一个能跑在上面的图"与"一个能跑起系统的图"是**两个不同强度的主张**，报告与设计里不许混用 |

## Part IV Method → Runtime 的演化分析

### IV.1 六级阶梯：每级究竟增加了什么

以严格的"增量"记法给出——**每一级只写它比上一级多出来的能力**。DSH 的现状已逐行核实（附录 A）。

| 级 | 名字 | 相比上一级**新增**的机制 | 状态在哪 | 谁决定下一步 | 能否停/恢复 |
|---|---|---|---|---|---|
| **L0** | **Prompt** | 无（一段文本） | 无 | 模型 | 不能（它就是一次输入） |
| **L1** | **Skill** | ①**可被发现**（名字+描述进目录）②**渐进披露**（metadata→body→附件，省上下文）③**两个调用面分别授权**（`modelInvocable`/`userInvocable` 四种组合）④**统一渲染**（`<skill_content>` 单一真源） | 无 | 模型 | 不能 |
| **L2** | **Workflow** | ①**控制流**（顺序/并行/流水线/阶段）②**可观察**（`workflow/*` 六个只读 emit）③**可取消、可释放到静止** ④**子工作的归属链**（每个 `agent()` 归属发起者）⑤**调用方设的上限**（`maxTotalAgents`，脚本看不见也换不掉） | 过程内，跑完即弃 | **模型写的脚本** | 只能取消，不能暂停 |
| **L3** | **Stateful Process** | ①**跨轮次持久状态**（goal：相位+revision+CAS；schedule：日志 fold + dispatch 事件）②**暂停/恢复**（paused/blocked；cold session 不工作、重开后重建 timer）③**不依赖模型回忆的触发点**（timer 到期 → 等 agent 完全 idle → 认领 maintenance phase → `followup()`；**绝不 `steer()`、绝不打断当前轮次**）④**推进/完成判定**⑤**每步等持久化 barrier**（失败报 `persistence_uncertain` 而不是猜）⑥**恢复的权威是日志的纯折叠** | **会话日志**（唯一权威） | **时钟 + 驱动器**决定"何时"，**内容仍是模型** | **能** |
| **L4** | **Interactive Environment** | ①**空间本身可被用户直接操作**②**用户的操作直接成为过程输入**（不只是对话）③**表征与过程合并到同一个可操作对象上**（用户改图 = 改状态）④**"看见"成为机制**而不是渲染细节 | 对象即状态 | 用户 + 模型 | 天然（存下就是停着） |
| **L5** | **Runtime Entity** | ①**能改变自己的运行方式**（运行时定义双半包：host 半进 `node:vm`、browser 半进页面）②**能创建其他实体**③**有版本与授权指针**（pluginId / 不可变 Package / current / next / grants）④**有诊断回路**（技术失败 → 读诊断 → 改同一 Plugin → 自主重试）⑤**可递归组合** | 进程内存（**不落盘、不过重启**） | 仍是模型 | **不恢复**（重启即消失） |

### IV.2 阶梯的真实形状（本文最重要的结构性发现）

把六级重排到两条**互不相干**的轴上：

```
轴 1｜"容器能力"：状态 观察 取消 恢复 自改     →   L0 ───────────→ L5    ✅ DSH 已到顶
轴 2｜"决策权归属"：谁主张下一步                →   模型 → 脚本 → 时钟 → ？   ❌ 停在半路
```

- **轴 1 上 DSH 已爬到 L5**：模型能在运行时定义、授权、挂载、卸载一个**双半包**，它可注册工具、提示词段、监听器、UI 槽位（`docs/tool-catalog.md:23,270,425`；`packages/extensions/README.md:5-9`）。
- **轴 2 上从来没有真正前进过**：`workflow` 是**模型写的脚本**在决定下一步；`goal` 是**驱动器按时把模型的轮次启起来**，但"下一步做什么"仍由模型产出。**Repo 里没有任何一处把决策权交给一个非模型的东西**——`packages/core/agent-loop` 是"唯一带具体循环逻辑的包"，而它是 LLM 驱动的 turn/step 工具循环。

> **所以 Sponge 要填的空白，精确地是轴 2 的下一格：一个非模型的东西主张"下一步"。** 这比"做可运行插件"精确得多——因为"可运行"是轴 1，**DSH 已经做完了**。

### IV.3 判据：什么时候一个"方法"必须变成一个正在运行的系统

四条可检验条件（J2 的实体化）：

| # | 条件 | 怎么测 |
|---|---|---|
| **C1** | 跨轮次状态被**宿主外部持有**（不靠模型记） | 关掉会话再开，状态还在吗？换一个模型，行为一致吗？ |
| **C2** | 存在**不依赖模型主动回忆**的触发点（时钟／事件／条件） | 用户什么都不说放三天，它会不会自己发生一次？ |
| **C3** | 存在**独立的"该不该推进／是否完成"判定** | 能否指出一行判定？判定失败时会怎样？ |
| **C4** | 状态**可被用户直接检视与操作** | 用户能指着界面说出"现在是第几步、下一格是什么"吗？ |

**用法**：命中 ≥2 条 → 值得做成运行对象；命中 <2 条 → **它就是一个 prompt/skill，做成插件只是包装**（"为改而改"）。

**五个实例跑一遍**：

| 实例 | C1 | C2 | C3 | C4 | 结论 |
|---|---|---|---|---|---|
| **苏格拉底法** | 弱（学习者状态） | 无 | 有（何时停止提问） | 无 | **1.5 条 → 不该做成运行对象**。正确形态 = Method（策略）+ Mode（角色）+ 一份**跨会话的学习者状态（那是域的职责，不是方法插件的私有状态）**——三者不是一个东西 |
| **WAM 六步循环** | 有 | 有（Wait 本身就是时钟） | 有 | 有 | **4 条 → 必须做成运行对象**。它是**方法论 + 状态模型**的组合，不是单纯 method |
| **结构重构法** | 有（重构产物） | 无 | 无 | 有 | **2 条 → 落点在 Representation × Method 的交界**：它是"在表征上施加的一组变换"（与 04 §六 通道＝图重写同源） |
| **研究方法（议程/假设/证据）** | 有 | 有 | 有 | 有 | **4 条 → 必须**。且它**要求跨插件共享状态**（论证图要读假设）→ **强制出现仲裁者**（见 Part VI） |
| **GEB 递归思考** | 无 | 无 | **有（深度控制：何时停止递归）** | 弱 | **1 条 → L1 足够**。它的"运行性"是假象；真正的内容是**递归深度与终止条件**，那是 Method 的一部分 |

### IV.4 一条否证线

如果某个"方法"装上之后，**说不出"不装它会更差"**，那么按 C1–C4 它必然 <2 条。**这条否证线同时也是 Sponge 能对外的第一句硬话**：不是"我们能装方法"，而是"**我们能判定一个方法到底需不需要被装**"。

### V.3 Sponge 计划里已经有的位置

见 §I.3 表。要强调的是：**`mechanism/`（scheduler · channel · agentpark）与 `content/`（element = callable unit）这两个占位，正好对应本文的两个空白**——`content/element` 是"装进去的东西"的物质载体，`mechanism/scheduler` 是"谁主张下一步"的调解器。**所以这次研究不需要改 02 的分类，只需要给这两个占位填上语义。**

### V.4 已解决 / 半解决 / 未解决

| 档 | 条目 |
|---|---|
| **✅ 已解决（别重造）** | 装配与依赖注入；可撤销；拦截与策略；服务可替换；组合分发（profile/bundle/patch/preset）；每会话不同能力；UI 声明与渲染（含座位声明与授权）；状态同步；时钟；后台工作；人机中断与审批；**运行时自改（含版本/授权/诊断）**；多主体协作基础设施 |
| **⚠️ 半解决** | ①**非会话的通用对象状态**：现在只有会话日志（全局唯一权威）与 `ctx.storage`（命名后端枢纽）——没有"**一个东西拥有一份自己的、可被别的东西读的状态**"这种对象；②**过程抽象**：goal/schedule/plan 三个先例各写一遍，没有共同抽象；③**对象级权限**：权限按过程/预设走，不按对象走；④**UI 的声明式形态**：只有 React 代码，没有"UI 即数据" |
| **❌ 未解决（唯一）** | **多个东西同时主张"下一步"时的调解。** DSH 对此只有一种机制：**`waterfall` 的监听器顺序**（按注册顺序，可用 `prepend: true` 插队、`bail` 短路）。这是"顺序"，不是"主张的调解"——没有优先级语义、没有冲突检测、没有解释、没有撤销后的重算 |

### V.5 抽象边界的判定：Plugin 只需描述语义，UI 能不能全交出去？

**结论：现在能，而且已经交出去了。** 边界如下——

| 归 Plugin 描述 | 归 DSH/Cordis 承担 |
|---|---|
| **语义**（我是干什么的、我的名字与识别符） | 装载顺序、依赖解析、作用域隔离 |
| **主张**（我要在什么粒度上主张下一步）←**这一条现在无处可写** | 渲染、组件生命周期、React 绑定 |
| **座位需求**（我要占哪个 UI 位置、是替换还是并列） | 槽位声明校验、冲突抛错、座位授权 |
| **状态需求**（我要持久化什么、谁能读我） | 序列化、日志落盘、恢复、barrier、fork 语义 |
| **触发需求**（我什么时候该被叫醒） | timer、idle 判定、maintenance phase 认领、`followup` 排队 |
| **能力需求**（我需要哪些能力引用） | 沙箱、审批、能力授予与撤销 |

**唯一不能交出去的**是**主张与调解**——因为它不是基础设施问题，是**秩序**问题：谁在什么条件下可以覆盖谁。DSH 有意不做这件事（它保持微内核中立），这正是 Sponge 该占的那一格。

## Part VI 组合、生命周期、调度、状态、权限

### VI.1 组合：不要在线性 vs 星形之间选（本文第二个硬结论）

你给的两个候选拓扑：

```
线性：  Research → Socratic → Argument Map → Todo
星形：          Sponge
              /   |    \
        Research Socratic Todo
                    |
              Argument Map
```

**现有系统在这两个拓扑上都有成熟答案，但失败模式也一样**：

| 拓扑 | 现实对应物 | 失败模式 |
|---|---|---|
| **线性（管道/中间件）** | Unix pipe；Koa/Express 中间件；**Cordis 的 `waterfall`** | 上游看不见下游；**下游失败无法回传上游**；每个中间层都以为自己知道全局 |
| **星形（黑板/中央调度）** | Hearsay-II 的 KS + 调度壳；K8s controller；LIDA 的竞争广播；AutoGen 的 selector | 必须有一个仲裁者；仲裁成本随数量增长；**仲裁者一复杂就变成新内核**（违反 J1） |
| **第三种（真实系统的常答案）：所有权分层** | **K8s：每个对象有 spec，controller 按对象写**；**seL4：每个引用有明确能力**；**OCap：每条边就是一次授权**；Erlang：每个进程只拥有自己的 mailbox 与状态 | "谁能写这个对象"成为唯一问题——**冲突变成权限问题，而不是顺序问题** |

> **结论（候选模型之一，非定案）：组合问题不是调用顺序问题，是写权限问题。** 线性 vs 星形只是**渲染出来的表象**；真正决定行为的是"**这份状态归谁**"。这与 §V.4 的 ⚠️①（没有对象级状态归属）和 Sponge 的「域 + 权限轴」正好接上。

**五类东西的组合冲突发生在五个不同的轴上**（矩阵 I 列的展开）：

| 轴 | 冲突形态 | 现有机制能否解决 |
|---|---|---|
| **策略轴**（Method×Method） | 两个策略都想主导提问方式 | 不能（`waterfall` 只能二选一或首尾相接） |
| **顺序/资源轴**（Workflow×Workflow） | 抢同一批子代理、同一批文件 | 部分（`maxTotalAgents` 是调用方上限；`writeScopes` 明确是**提示性的、不是锁**） |
| **投影同构轴**（Representation×Representation） | 两张图同构：思维导图 vs 论证图其实是同一份数据的两视图，谁是谁的视图？ | 不能（这是**建模问题**，不是运行时问题） |
| **状态归属轴**（Process×Process） | 两个过程都声称自己是某份状态的权威 | 不能（CAS revision 只防并发写，不解决"谁是权威"） |
| **人格轴**（Mode×Mode） | 导师 + 审阅者同时激活，说法自相矛盾 | 不能（没有优先级语义，也没有"合并人格"的算子） |

→ **一个统一的 priority 数字解决不了这五个轴。** 这是"统一必须在接口层、不能在机制层"的第二个证据。

### VI.2 生命周期

现有最完整的答案（跨领域，【二】级）：

| 需求 | 有证据的解法 | 出处 |
|---|---|---|
| 生命周期不是布尔量 | OSGi 六态；Orleans 激活/去激活（`OnActivateAsync` 在**状态装载之后、消息派发之前**） | §II.1 |
| 卸载要能回到装之前 | **一切注册都是 effect**（Cordis）；动态包 `stop` 会"dispose host 半到静止并撤回 browser 半" | `docs/cordis-primer.zh.md:13`；`packages/extensions/cordis-host-runner/README.md:15` |
| 更换/升级要带状态迁移 | Erlang `.appup` + `code_change/3`；Smalltalk `become:` + 活实例迁移；**动态包用不可变 Package + current/next 指针** | §II.5；`docs/tool-catalog.md:425` |
| 出错的正确反应 | **监督 = 重启回已知良好态**，而不是原地修复（"负责恢复的那部分应该无聊到没有 bug"） | §II.1 |
| 删除要能收尾 | **finalizer**（K8s）；`dispose()` 到静止（DSH：取消 + 有界结算 + 等子代理停稳，不因脚本卡死而挂起） | §II.1；`docs/subsystems/workflow.zh.md:95` |
| 只能有一个活跃者 | **leader election**（K8s）；`agentTeams` 用 `revision` 做 CAS | §II.1；`docs/subsystems/agent-team.zh.md:57` |

### VI.3 调度：谁决定下一步（核心问题 Q2）

| 答案 | 代表 | 代价 |
|---|---|---|
| 模型即兴 | 普通 agent loop | 长周期失败（2026-08 调研已量化的 C1 缺陷） |
| 模型写脚本 | DSH `workflow` | 只能一次性跑；无跨轮次状态；脚本是**代码不是数据**（不可检视、不可组合、"改一行"不可撤销） |
| 时钟 | `goal-round-driver` / `schedule` | 只解决"何时启"，不解决"启起来做什么" |
| 图/状态机 | LangGraph 谱系【待核】 | 图本身成为新的集中点；"谁能改图"是新的权限问题 |
| **黑板 + 调度壳** | Hearsay-II / BB1 | **唯一有长期证据的"多个主张者 + 一个调解者"形态**；代价是必须把调度本身也做成对象 |
| 竞争 + 广播 | GWT/LIDA | 需要**稀缺**（容量有限）才有竞争，否则退化成消息总线 |
| 能力式从属 | seL4 / OCap | 不解决"谁先说话"，解决的是"谁能做什么" |

> **可迁移结论（候选，非定案）**：Q2 的答案应该从**黑板谱系**取，而不是从工作流谱系取——因为黑板谱系是唯一把"多个独立的条件→动作模块"与"一个调度壳"分开建模的谱系，而它的表示**就是**基底，与"信息空间是本体"（02 §3.9）结构同构。
> **但必须补上黑板缺的那件事**：黑板假设知识源之间**不直接通信**、只通过黑板交互；而我们的东西会互相"说话"（导师要读研究议程）。所以还需要黑板没有的一条规则：**共享状态的写归属**（§VI.1 的第三种答案）。

### VI.4 状态：Plugin 该不该拥有自己的世界

对 §6 的问题（Research 的 hypotheses / evidence / questions / sources / agenda 到底是 Slice？Element？Plugin State？Domain？Scene？）——**给三个候选，并说明各自要求什么**：

| 候选 | 形式 | 它要求什么 | 先例 |
|---|---|---|---|
| **(a) 一个切片 + 若干子切片** | Research 是一个 Slice，五个集合各是它的子切片 | 需要先定"切片粒度"（06 P1-10）；需要子切片继承语义 | `研发/impl/src/base/slice.ts` 的 `subclass()`（内容继承 + parent 链）已支持；**但没有"这一份属于哪个域"的字段** |
| **(b) 一个切片 + 五种角色视图** | 状态只有一份，五个集合是**同一份状态的不同投影** | 需要"视图"成为一等概念（现在没有）；需要"谁写视图、谁写真相" | Hearsay-II 的黑板分层；`ui-slots` 的 `store` 座位（组件声明它读哪个 store，**但 store 归属仍未定**）；K8s 的 spec/status 分离 |
| **(c) 五个独立插件状态** | 每个集合归它自己的插件 | 需要跨插件共享机制；立刻出现"谁是权威" | Orleans 的 grain 私有状态（**但 grain 之间有明确消息边界**）；**这一条在本仓不成立**：动态包"只在进程内存、按会话可见、不过重启"（`packages/extensions/tool-cordis/README.md:19`），状态放插件里就**丢掉了"日志即权威"的不变量** |

> **判定（候选）**：**(a) 与 (b) 是同一件事的两面**——"子切片"是**存储视角**，"角色视图"是**访问视角**；而 **(c) 直接违反本仓已有的核心不变量**（会话日志是唯一权威 + "模型可见即已记录"）。
> 也就是说：**"插件拥有自己的世界"在本仓的前提条件下不成立，除非那个世界是"空间里的一份被归属了的状态"，而不是"插件私有的状态"。**
> 这需要"域"承担一个 02 目前没写明的职责：**域不只是存在模式，还可能是状态归属的单位。** ← 这是**唯一一处可能需要改 02** 的地方（见 §IX Q3）。

### VI.5 权限

| 现状 | 证据 | 结论 |
|---|---|---|
| DSH 权限是**过程级** | `ctx.sandbox` 后端、`ctx.approval`、permission-presets（`docs/cookbook/extension-cookbook.md:117-118`） | 装十个东西，它们共享同一个权限档 |
| DSH 有一处**能力式**授权 | `agentTeams` 用"**the exact live Agent**"当授权凭证；`writeScopes` 明确是"规范化的提示性路径前缀，**不是锁**"（`docs/subsystems/agent-team.zh.md:57,98`） | 这是本仓已有的正确方向，值得推广到插件层 |
| 跨领域铁律 | **声明要能力 ≠ 被授予权限**（OSGi/WIT/RBAC 都只是描述）；权限的正确物质形态是**引用本身**（seL4 CSpace / OCap）；seL4 已形式化证明 authority confinement | 权限不该写在 manifest 里，而该在**它拿到的引用**里 |
| 动态包的信任立场 | "**vm 沙箱隔离全局但不是安全边界**；把它当 bash 访问来对待"（`packages/extensions/cordis-host-runner/README.md:32`） | 运行时自改的安全底线已被本仓写下：**等于 shell 权限** |

## Part VII 五个互相竞争的抽象模型

五个模型是**互斥的解释**（不是五个定义）。每个都回答同一个问题："装进去的那个东西，本质上是什么？"注意：**它们不是最终设计**。

### H-A｜声明即运行时（Declaration-as-Runtime）

**一句话**：一个东西 = **一份声明 + 由它生成的实例**；装上 = 声明变成实例，卸下 = 撤销。五类的差别只是**声明 schema 的差别**，运行机制共用。

**机制落点**：Sponge `runtime/` 的 "dual form = config"（`研发/impl/PLAN.md:119`）；DSH `ui-slots` 的 "**Declaring is claiming**"（`packages/client/ui-slots/src/index.ts:141-143`）；Cordis 的"一切注册皆 effect"。
**最强外部先例**：**电子表格**——公式既是可读声明，又是可运行实例；这是有史以来最成功的最终用户编程系统。

### H-B｜主张者（Claimant）

**一句话**：一个东西 = 一个在**明确粒度**上主张"下一步／下一屏"的东西；统一的是**主张的表达与调解**，不是机制。

**机制落点**：**无处可写**——这是 §V.4 列的唯一 ❌ 项。现有最接近的是 `waterfall` 的注册顺序（弱到不能算）。
**最强外部先例**：**Hearsay-II 的知识源**（条件→动作，被黑板上的模式触发）+ **调度壳**；**BB1** 进一步把调度本身变成可推理对象。
**它的主张的实质**：不是"我要跑"，而是"**我认为现在该做 X，理由 Y**"——所以它天然要求**可解释**（对应 Norman 1994 的"agent 必须能说明意图"）。

### H-C｜域 + 视图（Domain + Views）

**一句话**：一个东西 = **一份被归属了的状态（域）上的一种访问模式（视图/角色）**；五类是同一状态的不同投影方式。

**机制落点**：Sponge 的**域** + 切片的 `subclass()`（`研发/impl/src/base/slice.ts:67`）+ `ui-slots` 的 `store` 座位。
**最强外部先例**：Hearsay-II 的黑板分层；K8s 的 spec/status 分离；Tana 的 supertag（**给节点打标签会真的触发效果**，是"行为挂在表示上"的现代唯一例子）。
**它的隐含赌注**：**"状态只有一份"**——所有东西都是这份状态的视图。

### H-D｜可执行表征（Executable Representation）

**一句话**：一个东西 = **一种能被某个解释器运行的表征**；五类是同一种"图"配不同的解释器（workflow=执行器、representation=渲染+校验器、process=时钟解释器、method=对话策略解释器、mode=输出过滤器）。

**机制落点**：Cordis 的类型化事件（表征变化 → 事件 → 解释器推进）；`ConversationNodeDefinition` 的状态机。
**最强外部先例**：**Harel 状态图 + SCXML/XState**（"方法有了正式表示 + 绑定解释器"的标准答案）；**SHACL**（闭合世界校验 + `sh:rule` 规则引擎）。
**必须注意的边界**：**IBIS／Toulmin 论证图至今没有解释器**——它们是"能跑在上面的图"，不是"能跑起系统的图"（§III.4 第三条）。

### H-E｜环境变换（Environment Transformation）

**一句话**：一个东西 = 对空间施加的**一类变换**；装上后，空间的**可达状态集**变了。五类是不同的变换族（改问法／改时序／改可见物／改权限／改角色）。

**机制落点**：Sponge 的**通道**（04 §六：连接是静态面、改造是动态面）+ 域迁移。
**最强外部先例**：**Unix 的"小语言"/DSL 传统**（文件是可参数化的对象，shell 是解释器）；**Nix**（一切皆从输入到产物的纯函数，产物按内容寻址）；**HyperCard**（"**脚本是 stack 里每个对象都有的一个属性**"，事件沿视觉层级上浮）——这是"变换挂在表示上"的最早干净案例。
**它的隐含赌注**：**"变换可以代数化"**——两个变换可复合、可化简、可比较。

### VIII.1 对照表（八个判据）

| 判据 | H-A 声明即运行时 | H-B 主张者 | H-C 域 + 视图 | H-D 可执行表征 | H-E 环境变换 |
|---|---|---|---|---|---|
| 能解释 Method | ✅ | ✅（主张问法） | ⚠️（无状态时勉强） | ✅ | ✅ |
| 能解释 Workflow | ✅ | ✅ | ⚠️ | ✅✅（最自然） | ⚠️ |
| 能解释 Representation | ✅ | ⚠️（它不主张"下一步"） | ✅✅（最自然） | ✅ | ✅ |
| 能解释 Persistent Process | ✅（声明出记录） | ✅✅（最自然） | ✅ | ⚠️ | ❌ |
| 能解释 Interaction Mode | ✅ | ✅（主张说法） | ❌ | ❌ | ✅ |
| **会不会引起架构膨胀** | 低（不新增机制） | 中（要新增"主张 + 调解"） | **高**（万物皆域 ⟹ 域变 god-object，风险与 02 §3.7 已记录的 god-class 风险同源） | **中高**（每个新东西要写解释器 ⟹ 解释器数量爆炸） | 高（"变换代数"很容易变成没人能用的抽象） |
| **与 Sponge 现行模型是否冲突** | 不冲突 | 不冲突（是空白，不是冲突） | **冲突**：02 §3.8 的域是"**存在模式**"，不是"状态容器" | **部分冲突**：02 §3.5 说原生表征是"**刻意轻、不预设内容类型**的脚手架"，而 H-D 要求每种类型有解释器 | 不冲突（与通道定义同源） |
| 能落到 DSH/Cordis | ✅（就是现有机制） | ⚠️ 落点不存在，需要在产品层之上新造 | ⚠️ 需要 `store` 归属语义 | ✅（类型化事件够用） | ✅（事件 + 域迁移） |
| 能支持 WAM | ✅ | ✅ | ✅ | ✅ | ⚠️ |
| **能支持"未来完全未知的东西"** | ✅✅（只要求有声明） | ✅✅（只要求会主张） | ❌（预设"有域"） | ❌（预设"有解释器"） | ⚠️（预设"是变换"） |

### VIII.2 各模型的诚实代价

| 模型 | 主要代价 | 主要未知 |
|---|---|---|
| **H-A** | **解释力强 = 判别力弱**：它几乎不排除任何东西，所以单靠它无法做设计决策 | 一份声明要到多细才能确定一个实例？"声明 → 实例"的映射失败时怎么办？ |
| **H-B** | 要新造两样东西（主张的表达 + 调解），而且**调解者一复杂就变成新内核**（违反 J1） | "主张"用什么粒度表达？冲突是**检测出来**还是**投票**出来？调解失败（两个都该做）时给用户看什么？ |
| **H-C** | **域会膨胀成万能对象**；并且与 02 现行定义冲突，改 02 的代价高 | 状态粒度（06 P1-10）不定，一切不能落地；"谁是权威"没有机制 |
| **H-D** | **解释器数量随内容类型爆炸**；与"脚手架刻意轻"的方向相反 | 解释器之间的**共享状态通道**不存在（两个解释器要读同一份数据怎么办） |
| **H-E** | 最抽象，**最容易写成没人能用的代数** | 变换能复合吗？可比较吗？恒等变换存在吗？（这三个答不出来就不是代数） |

### VIII.3 判别实例：哪个实例杀掉哪个模型

**这是本 Part 最有用的部分**——因为没有判别实例，五个模型就没有被区分开（违反 J3）。

| 判别实例 | H-A | H-B | H-C | H-D | H-E | 结果 |
|---|---|---|---|---|---|---|
| **六顶思考帽**（只改"说法"、不留状态、不主张下一步、无表征） | ✅ | ⚠️（须把"主张"广义化到"怎么说话"） | ❌ **无域无状态** | ❌ **无表征** | ✅ | **杀死 H-C、H-D** |
| **论证图**（用户直接操作 + AI 也写 + 需校验） | ✅ | ❌ **它主张"看见什么"，不主张"下一步"** | ✅✅ | ✅ | ⚠️ | **杀死 H-B 的狭义版本** |
| **研究议程**（权威状态 + 触发 + 催人） | ✅ | ✅✅ | ✅ | ❌ **议程不是被解释的表征** | ⚠️ | **杀死 H-D** |
| **苏格拉底法**（无状态策略 + 需要退出条件） | ✅ | ✅ | ❌ | ❌ | ✅ | 与六顶帽同 |
| **WAM 六步循环**（过程 + 产出 + 可反复跑） | ✅ | ✅ | ✅ | ✅ | ⚠️ | **都不能杀死它** → **WAM 的判别力最弱，不能当判别实例用** |
| **"今天该给我出哪 5 道复习题"**（据答题史决定；有状态/触发/判定/视图） | ✅ | ✅ | ✅ | ✅ | ⚠️ | 五个都能解释 → **常规情形区分不出模型** |

**读法**：能通过全部判别实例的只有 **H-A**（因为最弱）；**H-A 与 H-B 的乘积**（双形 + 主张者）也是；而 **H-C 与 H-D 各被两个实例杀死**。

> **所以：统一只能在接口层（双形 + 可撤销 + 主张），不能在机制层（五类需要三种不同运行时）。** 这不是妥协，是判别实例逼出来的结论。

### VIII.4 合成后的候选原语（非定案）

> **一个东西 = 一份声明（配置形态）→ 一个实例（运行形态）；它可挂载、可卸载（卸载回到装之前）；它在一个明确粒度上主张"下一步／下一屏"；空间负责主张的调解与状态的归属。**

五类的差别落在**三个装饰位**上（不落在本质上）：

| 装饰位 | 取值 |
|---|---|
| **主张的粒度** | 问法 ｜ 过程 ｜ 看见什么 ｜ 时序 ｜ 说法 |
| **状态的归属** | 无 ｜ 过程内 ｜ 对象即状态 ｜ 权威状态 ｜ 一个 bit |
| **运行时的种类** | 无 ｜ 执行器 ｜ 视图+校验器 ｜ 时钟+状态机 |

**并且明确否掉三种做法**：① 不把"声明即运行时"当成全部答案（太弱，判别不出东西）；② 不把五类合并成一个万能对象（三个装饰位不可消除）；③ 不把"插件自带世界"当成默认（违反本仓"日志即权威"不变量，见 §VI.4）。

### VIII.5 这个结论能不能撑住"未知的未来东西"

用 J1 测：假设明天要装一个**今天完全想不到的东西**（例：一个"按你情绪调整提问难度"的东西，或"把三个月前的对话按主题重新缝合"的东西）。按 §VIII.4 的合成——

- 它需要做三件事：写一份声明（它是什么、要什么）；说清它在什么粒度上主张什么；说清它需要什么状态与什么触发。**这三件事都不要求改内核** ✅
- 它**不需要**开发者去挑一个"这是 Method 还是 Process" ✅（这是最重要的一点：**分类不该是安装的前提**）
- 它会**触发**的未知：如果它同时需要"权威状态"和"视图"和"时钟"，它就是一个**复合体**——这时"三个装饰位"必须允许**一个东西同时占多个位**。**这是一个真正的开放问题，也是 §IX 的第一条。**

## Part IX 最值得继续验证的关键问题

按"能否证伪"排序，每条给出判据与当前证据状态。

| # | 问题 | 为什么关键 | 怎么判（可否证） | 当前状态 |
|---|---|---|---|---|
| **Q1** | **一个东西能不能同时占多个"装饰位"（复合体）？** | 若能，则"五类"根本不是分类，而是一张**装饰位组合表**——五类只是最常见五种组合。这会直接改写问题的问法 | 找出一个**必须**同时占三位的东西；再证明它**无法**被拆成三个独立东西（拆开后会丢什么？） | 无证据。WAM 是最像的候选（有过程+状态+视图），但它可能可拆 |
| **Q2** | **"主张冲突"是否真实发生？** | 若不发生，**整个调解问题不存在**，本文最重的结论（§IV.2 轴 2）就是臆造 | E1（§X）：装 5 个东西，统计冲突次数与人仲裁次数。**连续 10 次会话 0 冲突 → 假设被否** | 无数据。但间接证据支持它会发生：DSH 已经只能用"注册顺序"处理，说明设计者遇到过顺序问题 |
| **Q3** | **域要不要承担"状态归属"？** | **唯一可能需要改 02 的地方**（§VI.4）。若不要，则 §VI.1 的"所有权分层"没有落点 | 用 §VI.4 的 (a)/(b)/(c) 三候选对同一实例（研究议程）建模，看哪个能在**不改 02** 的前提下表达 | 02 §3.8 现在的域 = 存在模式；**(c) 已证不合本仓不变量** |
| **Q4** | **"装载 → 卸载"能否做到零残留？** | 这是"可撤销"这条共同结构的硬测试；做不到，则"装"就是不可逆的，用户会不敢装 | E4：卸完检查六处（日志/工具目录/UI 槽位/store/提示词段/定时器） | DSH 的 effect 机制**理论上**保证；**状态残留未验证** |
| **Q5** | **三个候选抽象能否用同一份最小实现同时跑通？** | 若能，说明它们**没被区分开**（违反 J3），需要找新判别实例；若不能，说明至少有一个是错的 | 同一组实例（§X E5 的 20 个）分别用合成模型 / H-C / H-D 分类，比较"无法分类"的数量 | 未做 |
| **Q6** | **判别实例集是否足够？** | 五个模型里有两个已被杀死，但**杀死它们的都是"轻"实例**（六顶帽、论证图）。需要**重**实例 | 找"至今没想到的东西"作为反例 | 见 Q1 |
| **Q7** | **声明式 UI 到底需不需要？** | 现在 DSH 只有 React 代码 + 类型化状态机（`ConversationNodeDefinition`）。如果"AI 主动改 UI"是核心场景，**代码能不能被 AI 稳定生成**就是关键分叉 | 观察 `cordis_define` 的 browser 半在真实使用中的失败率（渲染失败、越界、语义错误） | 本仓已有记录："**run 成功不代表 UI 渲染成功**"，渲染发生在 load 之后，失败要靠 `reportRenderFailure` 回读（`packages/extensions/cordis-host-runner/README.md:64`） |

## Part X 最小实验建议

**纪律（沿用已批准的诚实警告）**：**不自建公开基准、不做 SOTA 对比、不做完整实现**（对照 [roadmap §五](roadmap/2026-08-30-mvp-2-month.md)）。以下五个实验全部是**用现成机制就能做**的判别实验，目的是**证伪假设**，不是交付功能。

| # | 实验 | 假设 | 怎么做（全部用现成机制） | 通过 / 证伪标准 | 成本 |
|---|---|---|---|---|---|
| **E1** | **主张冲突探针** | Q2：多个"装载物"会真的争"下一步" | 同一会话里同时挂：① 一个 SKILL.md（方法）② plan-mode（模式）③ goal + schedule（过程）④ 一个 slots 面板（表征）。跑 5 个真实任务 | 记录：冲突出现次数、谁让步、是否需要人仲裁、模型是否察觉、用户是否察觉。**0 冲突 10 次 → Q2 被否，报告最重结论作废**（必须诚实接受） | 极低（无新代码） |
| **E2** | **撤除实验（fading / expertise reversal）** | 方法型装载物**必须自带退出条件**，否则对熟练者有害 | 同一任务，分两组（新手/熟练）× 两个条件（装苏格拉底法/不装），比较结果质量与用户主观负担 | 若熟练组"装"更差 → **fading 从理念变成数据**，且"退出条件"进入 primitive 的必填位 | 低（只需话术与评分表） |
| **E3** | **双形一致性** | "声明 → 实例"是可逆的（H-A 的前提） | 用一个表征类装载物：改声明 → 检查运行实例是否一致；再从声明**重建**实例，比对状态 | 重建失败 → H-A 的前提不成立，"双形"退化为类比修辞 | 低–中 |
| **E4** | **卸干净** | "可撤销"是共同结构（§III.3 第 2 条） | 装一个带状态的装载物 → 用 → 卸 → 检查六处残留：会话日志、工具目录（含 KV-cache 影响）、UI 槽位、store、提示词段、定时器 | 任一处残留 → "可撤销"只是理论承诺；用户会不敢装 | 低（检查清单 + 脚本） |
| **E5** | **判别实例集** | 合成模型（§VIII.4）比 H-C / H-D 更能容纳未知 | 收集 **20 个真实会想装进去的东西**（含 5 个"现在没有对应词"的），用三个模型各自分类 | **目标不是覆盖率，是找出反例**：出现"无法分类"或"必须占多个装饰位"的条目，就是 Q1/Q6 的答案 | 低（整理工作） |

**关于 E5 的一条方法提醒**：**不要用自己造的 20 个实例反复验证同一个模型**（这是自证）。20 个实例里必须有**至少 5 个来自"用户原话"**（不是我们归纳出来的类别），否则分类结果只是我们的分类学自我确认。

## 附录 B 跨领域证据要点（简）

> 来源：`general-purpose-3` 调研简报（PL/Runtime/KR/认知架构，2026-09-21）+ 本文整理。标注【二】= 二手权威；标【待核】= 通识，尚未逐条核对。

| 领域 | 关键事实 | 用途 |
|---|---|---|
| OSGi R8 | 六态生命周期；`Import-Package`／`Export-Package` 同时声明需要与提供 | "装"是状态机；声明是双面的 |
| Erlang/OTP | behaviour = 契约 + 回调；supervision 只负责恢复；**只能同时存在两个模块版本** | 监督 ≠ 业务；热更的真实上限 |
| Wasm Component Model | WIT 的 `world` **就是**能力声明；`resource` 有 `own`/`borrow` | 声明与授予分离 |
| Actor（Hewitt 1973） | actor 只拥有 mailbox + 私有状态 + 行为；可 `become` | 插件"自己的世界"的最小合法形态 |
| Orleans | grain 永不显式创建/销毁；`OnActivateAsync` 在状态装载后、派发前；持久 reminder | 激活时序；唤醒机制 |
| seL4 / OCap | 权限 = 引用本身；"only connectivity begets connectivity"；已证明 authority confinement | 权限的物质形态 |
| Kubernetes | spec/status 分离 + level-triggered 调和 + finalizer + leader election | 声明期望态 + 幂等 + 收尾 |
| Hearsay-II（1975/1980） | 黑板 + 条件→动作知识源 + 调度壳；KS 之间不直接通信 | **"表示即运行时"最强先例**；Q2 的答案应从这里取 |
| BB1 | 控制黑板（把调度当推理对象） | 调解器本身可以是对象 |
| Soar | 类型化 impasse → 子状态 → chunking | 没有调度器的另一种解法 |
| GWT / LIDA | 容量有限的工作区 + 竞争 + 广播 | 竞争需要稀缺 |
| SHACL（2017） | 闭合世界校验 + `sh:rule`/`sh:order` 规则引擎 | "可执行表征"的一个真实现 |
| IBIS（1970）/ Toulmin（1958） | 论证图**没有解释器** | "能跑在上面的图" ≠ "能跑起系统的图" |
| Harel 状态图（1987）/ SCXML / XState | 层次 + 并发 + 历史；可序列化可执行 | 方法获得正式表示 + 解释器的标准答案 |
| Erlang 热更 | `.appup` + `code_change/3`；监督 = 重启回已知良好 | 升级要带状态迁移 |
| Pluto.jl | 静态依赖分析 + 拓扑重算；**no hidden state** | 被动重算 vs 主动运行的分界 |
| HyperCard（1987） | "脚本是 stack 里每个对象都有的一个属性"；事件沿视觉层级上浮 | "行为挂在表示上"最早干净案例 |
| Tana supertag | 给节点打标签会**真的触发效果** | 唯一现代"行为挂在表示上" |
| Snakemake / Nextflow / CWL / Galaxy | 单元 = rule/process/CommandLineTool；用文件的时间戳或任务哈希做 resume | 过程的可恢复性靠什么 |
| W3C PROV（2013） | Entity/Activity/Agent；provenance 通常**是记录，不是驱动** | 把"记录"和"驱动"分清 |
